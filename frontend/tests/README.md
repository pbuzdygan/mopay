# Browser regression checks

Build the frontend with `npm --prefix frontend run build`, then run:

```sh
MOPAY_PLAYWRIGHT_MODULE=/absolute/path/to/an/installed/playwright \
  node --test frontend/tests/ui-transitions.mjs
```

The module can also be an existing `@playwright/test` installation. It must have its matching Chromium browser and system libraries available. If Playwright is already resolvable from the test directory, omit `MOPAY_PLAYWRIGHT_MODULE`. This focused check does not add project dependencies or a general test framework.

The check serves the production frontend build through browser request interception, supplies synthetic API fixtures, blocks service workers and intercepts external requests. It never starts the backend or uses real sessions or financial data.

Four desktop/mobile scenarios cover light/Normal and dark/Compact presentation, initial and cached table switches, rapid switching, New Entry opening/closing/reopening, and the entry, group and cell inspector (non-modal, no scrim, focus returns to the cell after Escape). Computed opacity is sampled on animation frames over a 650ms observation window to detect table dimming and fade reversals, including the native animation completion flash. Uncaught browser errors also fail the check.

These scenarios also sample saved collapsed groups during Expenses/Incomes switches, return from Savings and year changes, checking that expanded groups never appear in a painted frame and that manual expansion still works.

Four additional desktop/mobile light/dark scenarios exercise rejected PINs and successful unlocks with disposable mock credentials. The PIN overlay must fade monotonically and stay removed after login; no real authentication backend is used.

Set `MOPAY_SCREENSHOTS` to an existing temporary directory to capture rendered dialogs and the inspector. This is a Chromium presentation regression check; it does not verify API writes or reproduce GPU behavior on every browser/device.

Scenarios also render Savings and Overview (formerly Reports). For migration comparisons, `MOPAY_UI_DIST` selects a saved frontend build and `MOPAY_UI_METRICS` writes measured rectangles, colors, typography and spacing to a temporary JSON file. Use identical fixtures/viewports for both builds; generated captures and metrics stay outside Git/Docker contexts.

Both UI scenario groups serve assets with the backend's enforced CSP and fail on unexpected policy violations. After building, also run `node --test frontend/tests/browser-security.mjs` with the same Playwright environment. It starts a disposable loopback HTTP fixture with the actual header policy, verifies blocked inline/eval/external scripts and connections, checks a parent cannot frame the app, and exercises real service-worker registration, controlled reload, offline HTML/assets (including cached CSP) and blob downloads. It uses synthetic API responses and intercepts external connections; no production backend or credentials are involved. These Chromium checks are local gates, not currently installed in GitHub Actions.

Search checks cover Expenses/Incomes/Savings filtering, `/` and Ctrl/Cmd+K focus, Escape reset/blur, normal typing, and disabled Reports/PIN/modal cases. Mobile contexts enable touch/mobile emulation; below 960 px the app renders the mobile layout (top bar, bottom tab bar, More sheet, month list). The layout check covers the top bar and tab bar at 320, 390, 767px and 900x400 landscape (one row, 44 px targets, no page overflow, search opened by the shortcut). Captures assert visible editable fields have at least 16px computed text, including PIN, table/detail fields and dialogs. This checks the CSS condition associated with focus zoom; Chromium emulation does not reproduce a real iOS keyboard or prove Safari autofocus behavior. Manual pinch zoom remains enabled.

Four additional demo scenarios cover desktop/mobile light/dark presentation, failed metadata and retry, public demo PIN, disabled financial editing, read-only details, savings browsing, and demo/normal mode changes with expired cached sessions and independent year selections. Fixtures remain synthetic and API writes are checked separately by backend regressions.

For a full demo generator/API/UI check, install backend dependencies as well and run `node --test frontend/tests/demo-runtime.mjs` with the same Playwright environment. This check copies the backend into a disposable directory, binds only to loopback, generates its own synthetic demo database/key, and verifies desktop/mobile browsing and an XLSX download. It never opens the normal application database. Offline assets remain available, but application mode must be confirmed online before login; the browser security check verifies the Retry flow after reconnecting.

## Shared locators and feature parity

All browser checks import `ui-helpers.mjs`. Its locators use roles, accessible names and a few `data-testid` hooks (`entry-table`, `inspector`, `dialog-backdrop`, `pin-card`) instead of layout classes, so a redesign updates only the helper when a control moves. The `MOPAY_UI_METRICS` capture stays class-based on purpose: it measures the previous design for migration comparisons.

`node --test frontend/tests/ui-parity.mjs` (same Playwright environment, after building) covers the functions listed in the [UI migration parity inventory](../../.ai/plans/final-ledger-ui-migration.md#parity-inventory) that had no browser test: inline month values (including the parsing rules and save failures with Retry and Undo), totals and group totals, the Ungrouped section, the inspector drawer (cell selection, value and quick fill, entry/group details saved per field with errors, Retry and confirmed removal, tags, previous-year comparison) and the grid keyboard model (arrows, Home/End, Enter/typing/double-click editing, Tab, Escape, Shift+Enter, roving tabindex), Arrange (drag within a group and of groups, and keyboard reordering), Remove mode with its confirmation, cancel, failure and retry, tag notes as accessible cell descriptions, the grid summary strip, the empty-year message and that the grid needs no horizontal scrolling at 1440 px, savings goals (list and detail, add/edit with failure, removal dialog) and items (quick add with both types and failure cleanup, inline edit with failure, withdrawals, balance), Overview (KPIs and previous-year comparisons, month cards with best/weakest/current/no data, spending bars, savings overview, predictability, opening a month in Expenses with its cell focused, the empty state), the Settings page (year creation that switches the working year, year deletion with the protected working year, typed confirmation, backup reminder and failures, export and template downloads, import dialog, density, group totals, theme including System, About with *Check again*, encryption status, *Lock now*, Settings not persisted), the first-run year dialog with an empty year list, new group, the encryption notice/key mismatch dialogs and dialog keyboard handling (Escape, focus trap, focus return), and the desktop shell (sidebar navigation and totals with stacked sections, Overview start after load and unlock, working-year listbox, Edit/New menus, theme segment, Settings as current page, update link). Helpers pick the sidebar on desktop and the bottom tab bar and More sheet below 960 px; on the month list `showMonth` steps to a month, `selectCell`/`editValue` open the bottom sheet and `cellValue` reads a value on either layout. The mobile shell test covers the tab bar, More sheet, search icon and Actions menu. A stateful synthetic API records every write, so the checks compare request payloads as well as the rendered result. It runs at desktop light and mobile dark (dialogs in all four combinations); `MOPAY_SCREENSHOTS` also captures these states. XLSX validation, overwrite confirmation and import progress remain a manual check with a synthetic file.

`node --test frontend/tests/grid-render-baseline.mjs` measures how long the Expenses grid with 200 synthetic entries takes from a tab click to a painted grid (first load and cached switches, median of `MOPAY_GRID_RUNS`, default 7). It asserts no thresholds because timings depend on the host; set `MOPAY_GRID_METRICS` to a temporary JSON path and compare builds with `MOPAY_UI_DIST` on the same machine.
